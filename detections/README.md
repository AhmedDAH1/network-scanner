# Detecting NetScan

Rules that detect this project's own scanner, written from the defender's
side. Each one fires on real recorded NetScan traffic, stays quiet on a benign
baseline built to trip it, and is tested in CI so a change to the scanner or
the rules can't silently break it. Method and results: [TESTING.md](TESTING.md).

## Three layers

The rules sit at different levels of the
[Pyramid of Pain](https://detect-respond.blogspot.com/2013/03/the-pyramid-of-pain.html):
the higher the layer, the more an attacker has to change to evade it.

| Layer | Rule | What it matches | To evade it, an attacker must |
|---|---|---|---|
| Tool artifact | [Suricata sid 1000002](suricata/netscan.rules), [Sigma: web server](sigma/web_netscan_user_agent.yml) | `User-Agent: netscan/<version>` on the HTTP probe | Edit one string |
| Network fingerprint | [Suricata sid 1000001](suricata/netscan.rules) | Scapy's default SYN: source port 20, sequence number 0, window 8192, no TCP options | Change how probes are built |
| Behaviour | [Sigma: Zeek correlation](sigma/zeek_conn_vertical_port_scan.yml) | 25+ distinct ports rejected or unanswered on one host from one source within a minute | Scan slowly enough to stay under the threshold, whatever tool they use |

The first two say *which tool* it was, with almost no false positives. The
third detects port scanning in general, including NetScan with its
User-Agent and fingerprint changed. Production coverage needs the third;
the first two make triage faster.

## Using the rules

**Suricata 7:**

```bash
suricata -r capture.pcap -S detections/suricata/netscan.rules -l out/ -k none
jq 'select(.event_type=="alert") | .alert.signature' out/eve.json
```

To deploy, add the file to `rule-files` in `suricata.yaml`. SIDs 1000001 and
1000002 are in the local-rules range; renumber them if they clash with yours.

**Sigma:** convert with [sigma-cli](https://github.com/SigmaHQ/sigma-cli) or
pySigma. The correlation rule needs a backend that supports Sigma
correlations (Splunk and Elasticsearch ES|QL do; Lucene and Kusto don't).

## Converted queries

Generated by pySigma 1.5.1 from the rules in this folder (CI checks the
conversion still works).

**Splunk**

```
"cs-user-agent"="netscan/*"
```

```
proto="tcp" conn_state IN ("S0", "REJ")
| bin _time span=1m
| stats dc(id.resp_p) as value_count by _time id.orig_h id.resp_h
| search value_count >= 25
```

**Elasticsearch (ES|QL)**

```
from * metadata _id, _index, _version | where starts_with(`cs-user-agent`, "netscan/")
```

```
from * metadata _id, _index, _version | where proto=="tcp" and (conn_state in ("S0", "REJ"))
| eval timebucket=date_trunc(1minutes, @timestamp) | stats value_count=count_distinct(id.resp_p) by timebucket, id.orig_h, id.resp_h
| where value_count >= 25
```

In practice, replace `from *` with your Zeek and web server index patterns.

**Microsoft Sentinel (KQL)**

The Kusto backend can't convert correlation rules, so this one is written by
hand from the Sigma rule and is **not executed in CI**. Table and column names
depend on how Zeek logs are ingested; `ZeekConn` is a placeholder.

```kusto
ZeekConn
| where proto == "tcp" and conn_state in ("S0", "REJ")
| summarize value_count = dcount(['id.resp_p']) by bin(TimeGenerated, 1m), ['id.orig_h'], ['id.resp_h']
| where value_count >= 25
```

`dcount` is an estimate, accurate to a few percent at these sizes; use
`count_distinct` where your workspace supports it if the 25 boundary matters.
